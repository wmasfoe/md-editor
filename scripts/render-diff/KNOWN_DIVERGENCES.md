# 渲染差分：已知且显式接受的分歧

本文件记录**明确接受**的 TS/Rust 渲染差异。目的是落实目标中「若某项无法达到约定的
等价级别，停止并上报，**不得悄悄降低验收标准**」的要求：宁可显式登记，也不让
未记录的差异随绿测通过。

## 使用规则

1. 只有经过评估、确认「复刻成本远高于收益」或「TS 侧输出本身有缺陷」的差异才可登记。
2. 每条必须写明：输入形态、两侧输出、为什么接受、以及是否存在用户可见影响。
3. 差分测试（`scripts/render-diff`）与 `real-docs-parity.mjs` **不覆盖**这些形态；
   若将来要消除分歧，先从这里删除条目，再补 fixture。
4. 新增条目前必须确认它不属于目标点名的字节级类别：
   标题 ID/去重/legacy 别名、callout、`==highlight==`、代码高亮结构、数学公式、HTML 骨架。

## 当前登记项

### KD-1：相邻空 `$$` 块（`$$\n\n$$` 与其他 `$$` 块相邻）

**输入形态**：两个及以上 `$$` 块以空行分隔，且其中至少一个是空块（`$$\n\n$$`）。

```
$$x$$

$$

$$
```

**两侧输出**：

| 侧 | 输出 |
|---|---|
| TS（marked + 自定义 math 扩展） | `<p>$$x</p>` + `<div class="cm-md-math-block math-display"><span class="katex-error" …>` |
| Rust（comrak `math_dollars_block`） | `<p>$$x\n$$</p>` + `<div class="cm-md-math-block math-display"></div>` |

**为什么接受**：

1. **TS 侧输出本身是坏 HTML**：`katex-error` 表示 KaTeX 解析失败
   （`ParseError: Can't use function '$' in math mode`）。也就是说参照实现
   在这类输入上产出的是错误占位，不是可用渲染。
2. 分歧根源是 marked 自定义扩展 `start()` 的跨空行匹配，属于该扩展的实现瑕疵；
   在 Rust 侧复刻它等于**把缺陷固化**，违背「编辑器所见 = 导出所得」的初衷
   （编辑器在这类输入上同样显示解析错误）。
3. 该形态在实践中几乎不出现：连续两个空 `$$` 块不是有意义的文档内容。

**影响评估**：无实际用户可见影响（输入本身无意义，且 TS 侧输出为错误占位）。

**穷举验证**：`4×4 = 16` 种相邻 `$$` 组合中 7 例不一致，**全部**属于本类
（均已确认 TS 输出含 `katex-error`）。

### KD-2：行内代码内容含 `$$`

**输入形态**：行内代码里出现 `$$`（例如 `` `$$` ``、`` `a$$b` ``）。

**两侧输出**：

| 侧 | 输出 |
|---|---|
| TS | `<code class="…">a $$b</code>`（在 `$$` 前**插入一个空格**） |
| Rust | `<code class="…">a$$b</code>`（原样） |

**为什么接受**：

1. **TS 侧篡改了用户内容**：行内代码的语义是「原样显示」，插入空格直接改变了
   用户写的代码文本。这是 marked 自定义 `math_block` 扩展的 `start()` 命中行内
   位置导致的切分副作用。
2. 在 Rust 侧复刻它等于**主动破坏用户内容**，与「导出所得 = 编辑器所见」冲突。
3. 同一根因在 `:::` 上已确认是缺陷（见下），处理方式一致：**TS 侧缺陷不复刻**。

**影响评估**：TS 侧输出错误（多一个空格）；Rust 侧输出正确。属于「Rust 比参照
实现更正确」的分歧，接受。

**相关**：`:::` 的同类缺陷已在 TS 侧修复（`directive_container.start()` 只匹配
行首）；`math_block.start()` 的同类修复因会改动 4 条已固化 fixture 基准而暂缓，
待后续统一处理 TS 侧时一并修正。

### KD-3：两个 `$$` 块被其他内容隔开

**输入形态**：单行 `$$x$$` 之后隔着若干块内容，再出现另一个 `$$`（或独立 `$$` 块）。

```
$$m$$

---

```js
const a = 1;
```

$$m$$
```

**两侧输出**：

| 侧 | 输出 |
|---|---|
| TS | `<p>$$m</p>` + 一个 `math-display` 块，**块内吞掉了 `---` 与整个代码围栏** + 残留 `<p>$$</p>` |
| Rust | `<p>$$m\n$$</p>` + `<hr />` + 代码块 + `<p>$$m\n$$</p>`（结构与源码一致） |

**为什么接受**：

1. **TS 侧结构性错误**：`compileToTokens` 的 token 流直接暴露了这一点——
   `math_block` 的 `math` 字段是 `"---\n\n\`\`\`js\nconst a=1;\n\`\`\`"`，
   即分隔线与代码块被当成了公式内容。文档因此**丢失一个分隔线与一个代码块**。
2. 另有 50% 的同形态输入产出 `katex-error`（KaTeX 解析失败）。
3. 根因与 KD-1 相同：marked 自定义 `math_block` 扩展的 `start()` 在整个源串里
   找 `$$`，跨块匹配后把中间内容一并吞入。在 Rust 侧复刻等于固化该缺陷。
4. 该形态要求「两个 `$$` 之间夹着其他块」，实践中几乎不出现
   （仓库 364 份文档中 0 次；400 组随机组合 fuzz 中 4 次）。

**影响评估**：TS 侧丢失内容（分隔线、代码块）；Rust 侧保留。属「Rust 比参照实现更正确」。

## KD-4：四冒号嵌套指令 `::::note`

**输入**

```
::::note
:::tip
x
:::
::::
```

**TS**：`<p>:</p>` + `cm-callout--note`（正文 `<p>:::tip\nx</p>`）+ `<p>:</p>`
**Rust**：整段作为一段字面量文本输出

**成因**：TS 的指令正则固定匹配三个冒号。遇到四个冒号时，标记器的 `start()`
在偏移 1 处找到 `:::`，于是把首个 `:` 当作普通文本，从第二个字符开始匹配指令，
收尾的 `::::` 同理只吃掉三个冒号。Rust 侧判定「不是指令」而整体保留字面量。

**为何接受**

- TS 的行为本身是正则回溯的副产品，不对应任何有意义的书写意图；
- 仓库 364 份真实文档中该形态出现 **0 次**；
- 正确写法（三冒号）两侧完全一致，用户无需改变习惯。

若将来真实文档出现四冒号嵌套，应优先修 TS 侧的指令解析（用 `^:{3,}` 并记录
实际冒号数），而不是让 Rust 复刻这段偶然行为。
